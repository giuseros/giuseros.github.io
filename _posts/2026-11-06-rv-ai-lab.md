I said this blog wouldn't be about computer architecture. I lied a little: this one is about a CPU. But it's not a GPU, it's not work, and it's the most fun I've had with hardware in years.

I last wrote Verilog at university. Every so often I'd try to get back into it the obvious way: buy an FPGA board, write some RTL, flash it, and squint at an LED wondering why it isn't blinking. This time I did it the other way round, **simulation first**. Nothing goes near a board until it has been tested in a simulator, where I can see every signal on every clock cycle.

The result is a small RISC-V core, [**rv-ai-lab**](https://github.com/giuseros/rv-ai-lab), built together with Claude, one evening at a time.

## How the collaboration worked

It started with a strict split: I wrote the hardware, and Claude wrote the testbenches that tried to prove me wrong. That's how the register file, ALU, decoder, memory and control unit got built: me getting the Verilog wrong, the tests saying so, and a lot of "but *why* is that a latch?".

Halfway through I changed the deal. What I really want is to explore microarchitecture, not to type Verilog, so now Claude writes the RTL and I review it, asking questions until I understand every signal. "Explain this until I get it" turns out to be a great way to learn. (Full disclosure: early on, Copilot quietly autocompleted most of my ALU, which rather defeated the purpose. I switched it off for a while.)

## Tests that pass for the wrong reason

The most useful thing I learned isn't really about Verilog. Four times in this project, a test passed while the hardware was broken.

My favourite: the store-byte instruction wrote the wrong byte whenever the address wasn't word-aligned. The tests never noticed, because every byte store in them stored the value zero, and zero is zero in every byte position. The right answer and the wrong answer were the same.

So we started breaking the design on purpose. **Mutation testing**: change one line of the RTL in a realistic way, run the tests, and check that they fail. If a broken design still passes, you've found a hole in your tests. It found missing tests, some dead code, and one bug that could hide completely because a different block happened to mask it.

## Where it is now

The core runs one instruction per clock cycle. It sits in a small system: a bus with a proper valid/ready handshake, 16 KB of RAM, and a memory-mapped console. Every test program runs with memory answering instantly, one cycle late, and three cycles late, and has to produce exactly the same results, just slower:

~~~
$ make run PROG=count
0123456789
--- exit code 0: 36 instructions in 36 cycles (CPI 1.00) ---
~~~

Watching it print "hello" for the first time, five letters and a newline, was more satisfying than it had any right to be.

## What's next

Next up is running C programs compiled with GCC. After that comes the real point of the whole thing: using it as a lab. A pipelined version, caches, branch prediction, maybe a little matrix-multiply accelerator, each one measured against the simple core on the same programs.

Everything is on GitHub, including the full history of how the design evolved: [**giuseros/rv-ai-lab**](https://github.com/giuseros/rv-ai-lab).
